# テストケース設計

## RaiseTimeLine（仮称）

**この文書の役割:** 「どのテストケースを、なぜ選んだか」を残す。
テストの型・方針（どの層で何を確かめるか、使うアノテーション、命名規則）は
**`docs/tech-stack.md` の「バックエンドのテスト方針」「フロントエンドのテスト方針」が正本**なので、ここには書かない。

---

## 1. ケースの決め方

テストケースを思いつきで選ぶと、必ず抜けが出る。次の3つの技法で機械的に決める。

### 1-1. 同値分割

入力を「同じ結果になるグループ」に分け、**各グループから1つだけ**選ぶ。
投稿本文が「1〜280文字」なら、グループは3つ（短すぎ / ちょうどよい / 長すぎ）。
70文字と71文字を両方試すのは、同じグループなので無駄。

### 1-2. 境界値分析

**バグはグループの真ん中ではなく、切り替わり目に出る。**
`<=` と `<` の書き間違い、`length()` の数え方の間違いはすべて境目で起きる。
そこで各グループの**境目とその前後**を選ぶ。中間の値をいくつ試しても、この種の不具合は見つからない。

### 1-3. デシジョンテーブル

条件が複数あるときは、組み合わせを**表にして網羅**する。
「ログイン済み」「自分のものか」「存在するか」を頭の中で数えると必ず漏れる。
特に **403（権限がない）と 404（存在しない）の出し分け**は、表にしないと気づけない。

### 1-4. 「呼ばれないこと」の確認

例外が飛ぶことだけを確かめると、**「例外の前に書き込んでいた」場合を見逃す**。
弾いたときに、その先の処理（DB書き込み・ファイル保存・外部通信）が
呼ばれていないことを `verify(..., never())` で確かめる。

## 2. 投稿（`PostService` / `PostMapper`）

実装が持つ定数（`PostService.java`）: 本文の上限 **280文字** / ページの既定 **20件**・上限 **100件** / 新着取得の上限 **50件**

### 2-1. 本文の長さ（同値分割＋境界値）

| 入力 | 期待 | 狙い |
|---|---|---|
| `null` | `InvalidPostContentException` | 無効グループ |
| `""`・空白のみ・改行のみ | `InvalidPostContentException` | `isBlank()` の分岐 |
| 1文字 | 成功 | **下限ちょうど** |
| 280文字 | 成功 | **上限ちょうど** |
| 281文字 | `InvalidPostContentException` | **上限の外** |

### 2-2. ページサイズの正規化（境界値）

| `size` | 期待する要求件数 | 狙い |
|---:|---:|---|
| -1 | 21（既定20 + 1） | 負の値 |
| 0 | 21（既定20 + 1） | 下限の外 |
| 1 | 2 | **下限ちょうど** |
| 100 | 101 | **上限ちょうど** |
| 101 | 21（既定20 + 1） | **上限の外** |

> 常に「表示したい件数 + 1件」を要求する。余分に取れたかどうかで「次のページがあるか」を判定し、
> `COUNT(*)` を別途発行しないため。

### 2-3. ページ番号の正規化（境界値）

| `page` | 期待する `offset`（size=10） |
|---:|---:|
| -1 | 0（負は0ページ目として扱う） |
| 0 | 0 |
| 1 | 10 |
| 3 | 30 |

### 2-4. `hasNext` の判定（境界値）

**ここは20件と21件の境目でしか壊れない。**

| Mapper が返した件数（size=20） | `hasNext` | 画面に返す件数 |
|---:|---|---:|
| 0 | `false` | 0 |
| 20 | `false` | 20 |
| 21 | `true` | **20**（21件目は判定用なので返さない） |

新着投稿（上限50件）も同じ規則。**50件 → `hasMore=false` / 51件 → `hasMore=true`・50件を返す**。

### 2-5. 更新・削除の権限（デシジョンテーブル）

| # | 投稿が存在 | 自分の投稿 | 期待 | 確認すること |
|---|:---:|:---:|---|---|
| 1 | ❌ | − | `PostNotFoundException`（→404） | `updateContent` / `deleteById` を**呼ばない** |
| 2 | ✅ | ❌ | `PostAccessDeniedException`（→403） | 同上。画像削除も**呼ばない** |
| 3 | ✅ | ✅ | 成功 | 更新・削除が実行される |

> 投稿は公開情報なので、他人の投稿には 404 ではなく 403 を返して「権限がない」と明示する。
> 存在自体を隠したい種類のデータなら 404 に寄せる設計もある。

### 2-6. 画像の有無（デシジョンテーブル）

| 状況 | ファイル保存 | ファイル削除 |
|---|---|---|
| 画像なしで投稿 | **呼ばない** | − |
| 中身が空のファイルで投稿 | **呼ばない** | − |
| 画像ありで投稿 | 呼ばれる | − |
| **本文が不正で画像あり** | **呼ばない**（使われないファイルが残らないように） | − |
| 画像なしの投稿を削除 | − | **呼ばない** |
| 画像ありの投稿を削除 | − | 呼ばれる |

### 2-7. 新着件数の基準ID（境界値）

SQL は `id > afterId`。**基準となった投稿自身は数えない。**

| `afterId` | 期待 |
|---|---|
| 負の値 | 0 として扱う（初回読み込みと同じ） |
| 0 | 全件 |
| 最新の投稿ID | **0件**（新着なし） |
| 最新の1つ前のID | 1件 |

### 2-8. SQL の確認（`PostMapperTest`・実DB）

| 対象 | 確認すること |
|---|---|
| `insert` | `useGeneratedKeys` でIDがオブジェクトに書き戻される（直後に「作成した投稿を返す」ために必要） |
| `selectTimeline` | 新しい順・`LIMIT` で絞る・`OFFSET` で読み飛ばす・最終ページより後ろは空 |
| `selectTimeline` | いいね数／コメント数の集計・`likedByMe` が閲覧者ごとに変わる・未ログイン（`null`）でも動く |
| `selectFollowingTimeline` | フォロー中＋**自分の投稿**を含み、無関係な人は含まない |
| `selectByKeyword` | 中間一致・**`ILIKE` が大文字小文字を無視する**・エスケープ済み `%` が文字として扱われる |
| `updateContent` | 本文だけが変わり、画像はそのまま残る |

## 3. コメント（`CommentService` / `CommentMapper`）

本文の上限は投稿と同じ **280文字**。境界値も同じ（`null` / 空 / 1 / 280 / 281）。

### 3-1. 検証の順序

| # | 投稿が存在 | 本文 | 期待 | 理由 |
|---|:---:|---|---|---|
| 1 | ❌ | 不正 | **`PostNotFoundException`（404）** | 存在しない投稿に「本文が長すぎます」と答えるのは案内として誤り |
| 2 | ✅ | 不正 | `InvalidCommentContentException`（400） | |
| 3 | ✅ | 正常 | 成功 | |

### 3-2. 削除の権限（デシジョンテーブル）

| # | コメントが存在 | 自分のもの | 期待 |
|---|:---:|:---:|---|
| 1 | ❌ | − | `CommentNotFoundException`（→404）・**削除しない** |
| 2 | ✅ | ❌ | `CommentAccessDeniedException`（→403）・**削除しない** |
| 3 | ✅ | ✅ | 削除される |

### 3-3. SQL の確認

並び順は**古い順**（会話が上から読める順）。作成日時を明示して確認する
（`CURRENT_TIMESTAMP` はトランザクション開始時刻を返すため、続けて INSERT すると全部同じ時刻になる）。
投稿を削除するとコメントも `ON DELETE CASCADE` で消えることも確認する。

## 4. いいね（`LikeService` / `LikeMapper`）

### 4-1. 冪等性（このアプリの中核）

| 操作 | 期待 |
|---|---|
| 同じ人が2回いいね | **例外にならず件数は1のまま**（`ON CONFLICT DO NOTHING`） |
| 別の人がいいね | 件数が2になる（無視されるのは同一ユーザーの重複だけ） |
| いいねしていないのに取り消し | 例外にならない（0件削除） |
| 取り消し | 他人のいいねは消さない |

### 4-2. 存在確認の順序

投稿の存在確認を**先に**行う。後にすると、外部キー違反による 500 が 404 より先に発生してしまう。
→ 存在しない投稿へのいいねで `insertIgnoreDuplicate` が**呼ばれない**ことを確認する。

### 4-3. 件数と自分の状態は別の情報

`likeCount`（みんなの合計）と `likedByMe`（自分の状態）を取り違えない。
同じ投稿でも、見ている人によって `likedByMe` は変わる。

## 5. フォロー（`FollowService` / `FollowMapper`）

### 5-1. 自己フォローの防ぎ方（層の役割分担）

| 層 | 役割 | 確認すること |
|---|---|---|
| **Service** | **一次防衛** | `SelfFollowException` を投げ、**DBに問い合わせない** |
| DB（`ck_follows_not_self`） | 最後の砦 | Mapper を直接呼ぶと `DataIntegrityViolationException` |

> **DB制約に任せてはいけない理由:** `ON CONFLICT DO NOTHING` が無害化できるのは
> 一意制約違反（23505）だけ。CHECK制約違反（23514）は素通りして汎用ハンドラに落ち、**500** になる。

### 5-2. 向きの区別（非対称なデータで確認する）

フォローは「誰が誰を」の向きを取り違えやすく、**件数だけ見ていると気づけない**。
そこで**片思いの関係**を作って確認する。

| 一覧 | 含むもの | 含まないもの |
|---|---|---|
| `selectFollowing` | 自分がフォローしている人 | 自分をフォローしている人 |
| `selectFollowers` | 自分をフォローしている人 | 自分がフォローしている人 |

`followedByMe` は**閲覧者から見た関係**。相互フォローなら `true`、片思いされているだけなら `false`。

### 5-3. follow と unfollow の非対称性

`unfollow` には自己チェックが**無い**。解除は存在しない行を消すだけで害が無く、CHECK制約にも触れないため。
この違いは意図的なので、テストで固定しておく。

## 6. ユーザー・プロフィール（`UserService` / `UserMapper`）

### 6-1. @ユーザー名の重複判定（境界）

| 状況 | 期待 | 理由 |
|---|---|---|
| **自分が今使っている名前で保存** | **成功** | 除外しないと、表示名だけ直して保存しただけで409になる |
| 他人が使っている名前 | `UsernameAlreadyExistsException`（→409）・**更新しない** | |

### 6-2. アイコン更新の順序（順序そのものが仕様）

**「新ファイル保存 → DB更新 → 旧ファイル削除」**の順を守る。

> 逆順（旧削除が先）にすると、DB更新に失敗したときに**アイコンだけが失われる**。
> この不具合は「何が呼ばれたか」を見るだけでは検出できないため、`InOrder` で**順序**を検証する。

| 状況 | 旧ファイル削除 |
|---|---|
| 元々アイコンがある | 呼ばれる |
| 元々アイコンが無い | **呼ばない** |

### 6-3. 検索（`ILIKE`）

| 入力 | 期待 |
|---|---|
| `@ユーザー名`の一部 | 中間一致で見つかる |
| 表示名の一部 | 見つかる（username と display_name の OR 検索） |
| 大文字小文字を変えた語 | **見つかる**（`ILIKE` を使っているため） |
| エスケープ済みの `%`（`\%`） | **普通の文字として扱う**（`ESCAPE '\'` が効いていないと全件一致する） |
| 一致なし | 空のリスト（`null` ではない） |

## 7. 認証（`AuthService`）

### 7-1. 「何を返さないか」が重要

| 状況 | 期待 |
|---|---|
| メールアドレスが未登録 | `InvalidCredentialsException` |
| パスワードが違う | `InvalidCredentialsException`・**トークンを発行しない** |
| **上の2つのメッセージ** | **完全に同じ文言** |

> 「そのメールアドレスは存在しません」と返すと、**どのメールアドレスが登録済みかを教えてしまう**。

### 7-2. パスワードの保存

ハッシュが入っていることだけでなく、**生のパスワードが入っていない**ことも確かめる。
DBが漏れたときの被害の大きさが決定的に変わる部分のため。

### 7-3. リフレッシュトークン（デシジョンテーブル）

| # | トークンが存在 | 期限内 | ユーザーが存在 | 期待 |
|---|:---:|:---:|:---:|---|
| 1 | ❌ | − | − | `InvalidRefreshTokenException` |
| 2 | ✅ | ❌ | − | 例外 ＋ **そのトークンをDBから削除する**（使えない行を溜めない） |
| 3 | ✅ | ✅ | ❌ | `InvalidRefreshTokenException` |
| 4 | ✅ | ✅ | ✅ | 新しいアクセストークンを発行・**リフレッシュトークンは消さない** |

> **有効期限の判定は Service の責務で、SQL には期限の条件が無い。**
> `RefreshTokenMapperTest` で「期限切れでもレコードは返る」ことを明示的に確認し、
> 責任分担が変わっていないことを固定している。

## 8. 画像（`ImageValidator` / `LocalStorageService`）

### 8-1. サイズの上限（境界値）

上限は **5MB**（5,242,880バイト）。

| サイズ | 期待 |
|---|---|
| 0バイト | サイズを理由には拒否しない |
| ちょうど5MB | **受け入れる**（上限ちょうど） |
| 5MB + 1バイト | **拒否**（上限の外） |

### 8-2. 形式と拡張子（同値分割）

| Content-Type | 拡張子 | 期待 | 狙い |
|---|---|---|---|
| `image/jpeg` | `.jpg` / `.jpeg` | 受け入れ | |
| `image/png` | `.png` | 受け入れ | |
| `IMAGE/JPEG` | `.JPG` | 受け入れ | 大文字小文字を区別しない |
| `null` | `.jpg` | 拒否 | 未指定 |
| `text/plain` | `.txt` | 拒否 | 画像でない |
| `image/gif` | `.gif` | 拒否 | 画像だが許可外 |
| **`image/jpeg`** | **`.txt`** | **拒否** | **形式と拡張子の両方を見ている**（Content-Type は送信側が自由に名乗れる） |
| `image/jpeg` | なし | 拒否 | 拡張子が無い |

### 8-3. 保存（モックにしない）

「ファイルを保存する」処理をモックにすると、保存できたことにする処理をテストするだけになる。
`@TempDir` で一時ディレクトリに**実際に書き込んで**確認する。

| 確認すること | 理由 |
|---|---|
| 保存名が「UUID + 拡張子」 | |
| 元のファイル名を使わない | 同名衝突と日本語ファイル名を避けるため |
| 同名を2回保存しても両方残る | |
| 保存した中身が元と一致する | |
| **不正な形式ではファイルが作られない** | 例外だけ見ているとゴミファイルの残留を見逃す |
| 存在しないファイルの削除で例外を投げない | 削除は後片付け。失敗しても本来の処理は完了している |

## 9. 検索キーワード（`SearchKeyword`）

ここで防いでいるのは SQLインジェクションではない（MyBatis の `#{}` を使う限り起きない）。
防いでいるのは**「SQLは壊れないが検索の意味が壊れる」**問題。

| 入力 | 期待 | 狙い |
|---|---|---|
| `null` / `""` / 半角スペースのみ | `""`（空） | 呼び出し側が「DBに問い合わせない」と判断できる |
| `  鈴木  ` | `鈴木` | 前後の空白を除去 |
| `%` | `\%` | エスケープしないと `LIKE '%%%'` で全件に一致する |
| `_` | `\_` | LIKE では任意の1文字を表す記号 |
| `\` | `\\` | エスケープ文字そのものを打ち消す |
| **`\%`** | **`\\\%`** | **置換の順序の検証。** `\` を先に処理しないと、自分で足したエスケープ文字まで二重に変換されて意味が壊れる |

### 既知の課題

**全角スペース（U+3000）だけの入力は空扱いにならない。**
実装が使う `String#trim()` は U+0020 以下の文字しか取り除かないため。
半角スペースは空扱いなのに全角は違う、という不揃いな状態になっている。
直すなら `trim()` を `strip()`（Unicode対応版）に替えるだけだが、本番の振る舞いが変わるため、
テスト追加とは別に対応する。現状は `SearchKeywordTest` に「現状の挙動」として記録してある。

## 10. フロントエンドの API 層とフック

画面の見た目ではなく、**画面の裏で動く通信の組み立てと判断**のケース設計。
どの層で何を差し替えるか（`fetch` を差し替えるのか、モジュールごと差し替えるのか）は
`docs/tech-stack.md`「フロントエンドのテスト方針」が正本。

### 10-1. リクエストの組み立て（`apiRequest`・デシジョンテーブル）

| # | `body` | `accessToken` | `Content-Type` | `Authorization` |
|---|---|:---:|---|---|
| 1 | なし | なし | 付かない | 付かない |
| 2 | オブジェクト | なし | `application/json` | 付かない |
| 3 | **`FormData`** | なし | **付かない** | 付かない |
| 4 | オブジェクト | あり | `application/json` | `Bearer xxx` |
| 5 | `FormData` | あり | **付かない** | `Bearer xxx` |

**#3・#5 がこの表の主目的。** `multipart/form-data` の区切り文字（boundary）はブラウザが自動生成する。
手で `Content-Type` を書くと boundary が欠け、**サーバーが本文を読めなくなる**（＝画像付き投稿が壊れる）。
「付ける」ではなく**「付けない」ことが仕様**なので、付いていないことを検証する。

### 10-2. レスポンスの解釈（`apiRequest`・同値分割）

| レスポンス | 期待 | 狙い |
|---|---|---|
| 成功・本文 `{"id":1}` | オブジェクトを返す | 正常系 |
| 成功・**本文が空** | `undefined` を返す | 削除API（204）。`JSON.parse('')` は例外になるため分岐が要る |
| 失敗・`{"message":"..."}` | `ApiError(status, その文言)` | サーバーの文言をそのまま画面に出す |
| 失敗・**壊れたJSON** | `ApiError(status, '通信中にエラーが発生しました')` | サーバー停止時のHTMLエラーページなど |
| 失敗・`message` を持たないJSON | 同上 | 既定文言へのフォールバック |

### 10-3. 401 のあとの再試行（`useAuthorizedRequest`・デシジョンテーブル）

アクセストークンの期限切れは**手動では再現しづらい**（実際に期限が来るまで待つ必要がある）。
表で条件を網羅し、自動テストで固定する。

| # | `accessToken` | 1回目の結果 | `refreshToken` | リフレッシュの結果 | 期待 |
|---|:---:|---|:---:|---|---|
| 1 | **なし** | − | − | − | 401 を投げ、**通信そのものを行わない** |
| 2 | あり | 成功 | あり | − | 結果を返し、**リフレッシュしない** |
| 3 | あり | `ApiError(500)` | あり | − | そのまま投げ、**リフレッシュしない** |
| 4 | あり | `ApiError(401)` | **なし** | − | そのまま投げ、**リフレッシュしない** |
| 5 | あり | `ApiError(401)` | あり | **成功** | 新トークンを保存し、**新トークンで**再試行して結果を返す |
| 6 | あり | `ApiError(401)` | あり | **失敗** | ログアウトし、**最初の401**を投げる |
| 7 | あり | `ApiError` 以外の例外 | あり | − | そのまま投げ、**リフレッシュしない** |

**#3・#4・#7 は「呼ばれないこと」の確認。** 401以外でもリフレッシュしてしまう実装は、
正常系のテストだけでは絶対に検出できない（結果は同じで、無駄な通信が増えるだけのため）。

**#5 では「新しいトークンで」再試行しているかまで見る。** 古いトークンを使い回す実装でも、
モックが成功を返せばテストは緑になってしまう。呼び出し引数を検証してはじめて固定できる。

### 10-4. URL とクエリの組み立て（`postApi`）

| 入力 | 期待 | 狙い |
|---|---|---|
| `searchPosts` に `&` を含むキーワード | `q=a%26b` | **エスケープ漏れはクエリを壊す。** `q=a&b` だと後半が別パラメータになりサーバーに届かない |
| `searchPosts` に日本語・`#` | パーセントエンコードされる | 同上 |
| `fetchTimeline(mode='following')` | `&timeline=following` が付く | 分岐 |
| `fetchTimeline(mode='all')` | `timeline` が**付かない** | **分岐の裏側。** 常に付ける実装を検出するため |
| `createPost` 画像あり | `FormData` に `content` と `image` | 分岐 |
| `createPost` 画像 `null` | **`image` キーが無い** | **分岐の裏側。** 空の値を送るとサーバーが「サイズ0のファイル」と解釈しかねない |

> **「分岐の裏側」を必ず対にする。** 「付ける側」だけを確かめると、
> 常に付ける実装でもテストが通ってしまい、条件分岐そのものは何も守られない。

## 11. フロントエンドの UI コンポーネント（ユーザー操作）

画面の部品のうち、**ユーザーの操作を受け取るもの**のケース設計。
表示だけの部品と違い、境界値・二重送信・確認ダイアログといった判断が入る。

### 11-1. 投稿本文の長さ（`PostComposer`・同値分割＋境界値）

実装が持つ上限は **280文字**（`MAX_CONTENT_LENGTH`）。バックエンドの `PostService` と同じ値。

| 入力 | 期待 | 狙い |
|---|---|---|
| 0文字 | 投稿ボタンが押せない | 下限の外 |
| 空白のみ | 投稿ボタンが押せない | `trim()` の分岐 |
| 1文字 | 押せる | **下限ちょうど** |
| 280文字 | 押せる・残り「0」 | **上限ちょうど** |
| 281文字 | **押せない**・残り「-1」 | **上限の外** |

> **残り文字数は「0」と「マイナス」の両方を確かめる。** 超過分をマイナスで示さないと、
> 「あと何文字消せばよいか」が分からなくなる。

### 11-2. 画像の形式とサイズ（`PostComposer`・境界値）

上限は **5MB**（`5 * 1024 * 1024`）、許可形式は **JPEG と PNG** のみ。

| 入力 | 期待 |
|---|---|
| 5,242,880 バイト（5MBちょうど） | 受け付ける（判定が `>` のため） |
| 5,242,881 バイト | エラーを表示し、**プレビューを出さない** |
| `image/gif` | エラーを表示し、**プレビューを出さない** |
| `image/png` / `image/jpeg` | プレビューを出す |

> **エラー表示だけでなく「プレビューが出ないこと」まで見る。**
> メッセージは出るのにファイルは保持されている、という中途半端な状態を防ぐため。

> **形式チェックのテストだけ `fireEvent` を使う。** `input` の `accept` 属性により、
> `userEvent` は実際のブラウザと同じく GIF を渡してくれず、検証したいコードに到達しない。
> `accept` はブラウザ任せの一次防衛にすぎないので、**それをすり抜けたときに働く二重の守り**を確かめる。
> （DB制約が最後の砦であって一次防衛ではないのと同じ考え方）

### 11-3. フォローと解除の非対称（`FollowButton`・デシジョンテーブル）

| # | `followedByMe` | 操作 | 期待 |
|---|:---:|---|---|
| 1 | false | ― | 「フォローする」と表示 |
| 2 | true | ― | 「フォロー中」と表示 |
| 3 | false | クリック | **すぐ** `followUser` を呼ぶ（確認しない） |
| 4 | true | クリック | **確認ダイアログを出すだけ**。`unfollowUser` は呼ばない |
| 5 | true | クリック→キャンセル | `unfollowUser` を**呼ばない** |
| 6 | true | クリック→実行 | `unfollowUser` を呼び、`onChanged` を呼ぶ |
| 7 | false | クリック→失敗 | `onError` を呼び、`onChanged` は**呼ばない** |
| 8 | true | クリック→実行→失敗 | **ダイアログ内**にエラーを表示（`onError` は呼ばない） |

> **#3 と #4 の非対称が仕様。** フォローはやり直せるので即実行、解除は取り消しにあたるので確認を挟む。
> ここを揃えてしまう変更を検出したい。

> **#7 と #8 でエラーの見せ方が違うのも仕様。** 解除の失敗はダイアログを開いたまま理由を見せ、
> その場で再試行できるようにする。実装側にもその意図がコメントで書かれている。

### 11-4. 「消えないこと」「戻ること」（全コンポーネント共通）

失敗したあとにユーザーが困らない状態へ戻るか。**成功側だけを見ていると気づけない。**

| 状況 | 期待 | 理由 |
|---|---|---|
| コメント送信が成功 | 入力が**空になる** | 次を書ける |
| コメント送信が**失敗** | 入力が**消えない** | 消えると書き直しになる |
| 投稿の送信が失敗 | 画面を**閉じない**・本文も残る | 閉じると書いた本文ごと消える |
| 削除の実行が失敗 | エラーを表示し、ボタンが**再び押せる** | 押せないままだと閉じることも再試行もできない |
| いずれも失敗のあと | **もう一度実行できる** | 一度の失敗で操作不能にならない |

### 11-5. 二重送信の防止（全コンポーネント共通）

通信が終わる前にもう一度押せると、同じ投稿・コメントが2件登録される。

| 対象 | 検証 |
|---|---|
| `PostComposer` | 送信中は投稿ボタンと閉じるボタンが押せない／連打しても `onSubmit` は1回 |
| `CommentForm` | 送信中は送信ボタンが押せない／連打しても `onSubmit` は1回 |
| `DeleteConfirmDialog` | 実行中は実行・キャンセル・閉じるがすべて押せない／連打しても1回 |
| `FollowButton` | 通信中はボタンが押せない／連打しても `followUser` は1回 |
| `LikeButton` | 通信中はボタンが押せない／連打しても `onToggle` は1回／成功・失敗どちらでも押せる状態に戻る |

> **`LikeButton` は他の4つと構造が違う。** 自分では通信せず、親（各ページ）が通信する。
> そのため「通信が終わったこと」を知る手段が無く、対策を入れようにも書けない状態だった
> （`onToggle: () => void` は戻り値を捨てる型）。Issue #75 で
> `onToggle: () => void | Promise<void>` に広げて待てるようにしてから `disabled` を入れた。
> **props の型が実態と合っていないと、書きたい処理そのものが書けなくなる**という例。
> 呼び出し元4か所は元から `async` 関数を渡しており、型を広げるだけで変更不要だった。
>
> **`LikeButton` にだけ `disabled:opacity-50` を付けていない。** 他の4つは数百ms〜秒かかる
> 重い操作なので「処理中」と見せる価値があるが、いいねは連打される軽い操作で通信が数十msで
> 終わるため、その間だけ半透明にすると点滅して見えるだけになる。

### 11-6. 現状の挙動として記録するもの（仕様は変えない）

- **`DeleteConfirmDialog` は成功時に「実行中」表示のまま**になる。親が閉じる前提の設計。
  この前提が崩れると画面が固まって見えるため、現状をテストに残す
- **`Esc` キーで閉じる機能は実装されていない**（`ModalOverlay` にキー操作の処理がない）。
  存在しない機能はテストできないため対象外とした
- **一度表示したエラーメッセージは、次の操作が成功しても消えない。**
  成功したときに `setError(null)` を呼んでいないため。いいねを扱う4画面すべてが同じ挙動で、
  他の操作（投稿・フォロー等）も同様。Issue #77 で気づいたが、**同Issueでは直さない**。
  理由は、4画面共通の挙動をいま2画面だけ直すと**再び画面ごとに食い違う**ため。
  直すなら「エラー表示の消し方」として全画面まとめて扱う

### 11-7. いいねの失敗を画面に伝える（4画面の統一・Issue #77 で解決）

Issue #75（二重送信）の修正中に「失敗しても押せる状態に戻る」テストを書いて見つかった不具合。
**`TimelinePage` と `PostDetailPage` は、いいねの通信が失敗しても画面に何も表示しなかった。**

| 画面 | 修正前 | 修正後 |
|---|---|---|
| `ProfilePage` | `try/catch` → `setError`（正しい） | 変更なし |
| `PostSearchResults` | `try/catch` → `setError`（正しい） | 変更なし |
| `TimelinePage` | **`catch` が無く、何も表示しない** | `try/catch` → `setError` |
| `PostDetailPage` | **`catch` が無く、何も表示しない** | `try/catch` → `setError` |

> **`LikeButton` に `onError` を足す案は採らなかった。** `FollowButton` は**自分で通信する**ため
> 失敗を知っているのは自分だけで、親へ伝える口が要る。一方 `LikeButton` は**自分では通信しない**
> （通信するのは親）。失敗を最初に知るのも親なので、いったん子へ渡して子から親へ返すのは遠回りになる。
> 加えて、既に正しく動いている2画面の `catch` を消して書き直すことになり、変更が2→6ファイルに増える。
> **すでに多数派の書き方があるなら、そちらへ寄せる。**

> **`LikeButton` の空の `catch` は残す。** 受け取らずに投げっぱなしにすると Unhandled Rejection になり、
> **テストは緑なのに終了コードだけ 1 になる**（**緑色は品質の保証ではない**の実例。Issue #75 で遭遇）。
> 呼び出し元4画面はいずれも自分で `catch` するようになったが、将来 `catch` を書き忘れた
> 呼び出し元が現れたときの受け皿として残している。

#### ケース設計（`TimelinePage` / `PostDetailPage` の2画面で同じ4ケース）

`frontend/src/pages/` に置く**画面のテストはここが最初**。画面全体を網羅するのではなく、
いいねの失敗に関わる部分だけに絞る。投稿カードといいねボタンは単体テスト済みのため本物を使う。

| 入力（通信の結果） | 期待 | 狙い |
|---|---|---|
| 成功する | いいね数が最新値に更新される | 成功パスが動いていること自体の確認 |
| 成功する | **エラーメッセージを表示しない** | **分岐の裏側** |
| `ApiError` で失敗 | サーバーが返した文言を表示する | 出どころのある理由はそのまま見せる |
| `ApiError` 以外で失敗 | 「通信中にエラーが発生しました」を表示する | サーバーに届いていないときの既定文言 |

> **成功ケースを必ず対で書く。** 失敗ケースだけだと「常にエラーを出しっぱなしの実装」でも
> 緑になり、テストが何も保証しなくなる。
>
> **成功ケースは「通信が終わったこと」を待ってから判定する。** いいね数の更新を
> `findByRole` で待ってからエラーの不在を確かめる。待たずに判定すると
> **「まだ何も起きていないだけ」で緑**になり、これも何も検証していないテストになる。

> **赤の確認は壊し方を変えて3回行った**（Issue #77）。修正前＝失敗系4件が落ちる／
> `err instanceof ApiError` の分岐を潰す＝`ApiError` の2件だけ落ちる／
> 成功時にも `setError` を呼ぶ＝裏側の2件だけ落ちる。
> **壊し方ごとに落ちる組み合わせが変わることで、8件すべてが意味を持つと確認できる。**

## 12. フロントエンドの UI コンポーネント（表示）

画面の部品のうち、**渡されたデータをどう見せるかを担当するもの**のケース設計。
操作系（11章）が「押したら何が起きるか」を問うのに対し、こちらは「**この入力ならこう見えるか**」を問う。

### 12-1. アイコンの頭文字（`Avatar`・境界値）

画像が未設定のときは表示名の先頭1文字を丸の中に出す。

| 入力 | 期待 | 狙い |
|---|---|---|
| `iconImageUrl` あり | 画像を出す。頭文字は**出さない** | 分岐の表 |
| `iconImageUrl` が `undefined` / `null` / `""` | 頭文字を出す | 「未設定」の3通りを同値として確認 |
| 表示名 `""` | 「?」 | **下限の外** |
| 表示名 `"   "`（空白のみ） | 「?」 | `trim()` 後に空になる**境目** |
| 表示名 `"  鈴木  "` | 「鈴」 | 前後の空白を無視する |
| 表示名 `"🍣寿司太郎"` | 「🍣」 | サロゲートペアが壊れない |

> **絵文字は内部的に2つの値の組で表される（サロゲートペア）。** 単純に1文字目を取り出すと
> 壊れた文字になるため `Array.from` で分解している。この対策を外すと絵文字のケースだけが落ちる。

> **この部品だけ `container.querySelector('img')` を使う。** アイコンは隣に名前が書いてある飾りなので
> `aria-hidden="true"` を付けて読み上げの対象から外しており、`getByRole` では取得できない。
> **「読み上げさせない」こと自体が仕様**であるため、ここでは方針の例外として扱う。

### 12-2. 入力欄と親のやりとり（`FormField`）

| 検証 | 理由 |
|---|---|
| ラベルの文字から入力欄をたどれる | ラベルを押して入力に移れる。読み上げでも項目名が分かる |
| `type` が反映される | `password` が伏せ字にならないと、画面を見られただけで漏れる |
| `autoComplete` が反映される | ブラウザの自動入力がどの項目かを判断する手がかり |
| `onChange` が**イベントではなく文字列**で呼ばれる | 呼ぶ側が `event.target.value` を書かずに済ませるための約束 |
| `error` の有無でメッセージが出る／出ない | 片側だけだと、常に出す実装でも緑になる |
| `error` が空文字なら要素ごと作らない | 空の要素が残ると余白がずれて見た目が崩れる |

> **`onChange` の約束は明示的に固定する。** ここを崩すと、この部品を使っている
> ログイン・登録・プロフィール編集の各画面が**同時に**壊れるが、部品自身は「入力できる」ままなので気づけない。

### 12-3. 相対時刻の置き場所（`TimeAgo`）

**相対時刻の境目（59秒 / 60秒 / 24時間など）はここでは書かない。**
`formatDateTime.test.ts`（9章の下）で 0 / 59 / 60 / 3599 / 3600 / 86399 / 86400 秒をすでに確認済みで、
`TimeAgo` 自身は計算をせず結果を `<time>` 要素に載せるだけだからである。
**同じ仕様を2か所に書くと、片方だけ直したときに食い違う。**

| 置き場所 | 期待 | 誰のためか |
|---|---|---|
| 本文 | 「2時間前」 | 目で見る人 |
| `dateTime` 属性 | 渡した ISO 文字列そのまま | 読み上げソフト・検索エンジン |
| `title` 属性 | 「2026/06/15 10:00」 | マウスを乗せた人 |

> **本文が日付表示に変わっても `dateTime` には時刻まで残る**ことを別ケースで確認する。
> 画面の「6月13日」だけでは、機械には何時の投稿か分からない。

### 12-4. 新着件数の丸め（`NewPostsBanner`・境界値）

| 入力 | 期待 | 狙い |
|---|---|---|
| 0件 | 「↑ 0件の新着を表示」 | 下限の外（呼ぶ側は出さないが部品として壊れない） |
| 1件 | そのまま表示 | 下限ちょうど |
| **99件** | **そのまま表示** | **上限ちょうど** |
| **100件** | **「99+」に丸める** | **上限の外** |
| 読み込み中 | 「読み込み中…」・件数は**出さない**・押せない | 連打で同じ読み込みが何度も走るのを防ぐ |
| 読み込み中でない | **押せる**・`onClick` が呼ばれる | 「押せない」の裏側 |

> 判定は `count > 99`。`>=` に書き換えると **99件のケースだけ**が落ちる。

### 12-5. 検索結果の表示分岐（`PostSearchResults` / `UserSearchResults`・デシジョンテーブル）

2つの部品は担当するデータが違うだけで、分岐の形は同じ。

| # | `keyword` | 通信の結果 | 期待 |
|---|:---:|:---:|---|
| 1 | 空文字 | （通信しない） | 案内文を出し、検索APIを**呼ばない** |
| 2 | あり | 成功・1件以上 | 結果を並べる |
| 3 | あり | 成功・0件 | 「見つかりませんでした」 |
| 4 | あり | `ApiError` | **サーバーが返したメッセージ**を出す |
| 5 | あり | それ以外の失敗 | 「通信中にエラーが発生しました」 |
| 6 | あり | 失敗 | 前の検索結果を**残さない** |

> **#4 と #5 を分けるため `ApiError` は本物を使う**（`api/client` はモックしない）。
> 丸ごと偽物にすると `err instanceof ApiError` の判定が成立せず、この2つを区別できない。

> **`PostSearchResults` は `isOwn` の計算も持つ。** 自分の投稿には編集ボタンが出て、
> 他人の投稿には出ないことを対で確認する。**出す側だけだと、誰の投稿にも出す実装でも緑になる。**

### 12-6. 通信の追い越し（レース条件）

**先に投げた通信が後から返ってくることは実際に起きる。**
「す」を検索している最中に「すず」まで入力が進むと、遅れて返った「す」の結果で
画面が上書きされ、**入力した文字と表示された結果がずれる**。

両コンポーネントはこれを `ignore` フラグ（`useEffect` の後片付けで立てる印）で防いでいる。

| 手順 | 期待 |
|---|---|
| 「す」の検索を遅らせたまま「すず」へ進める | 「すず」の結果が出る |
| そのあと「す」の結果が返る | **画面は「すず」の結果のまま変わらない** |

> **この4行は、消しても他のテストが1件も落ちない場所だった。** 一見「無くても動く」ため、
> 将来「不要なコード」と誤解されて消される危険がある。**入っている対策をテストで固定する**のが目的。

### 12-7. ルートの門番（`ProtectedRoute` / `GuestRoute`・デシジョンテーブル）

| # | 部品 | `isAuthenticated` | 期待 |
|---|---|:---:|---|
| 1 | `ProtectedRoute` | false | `/login` へ送る。**守っている中身は出さない** |
| 2 | `ProtectedRoute` | true | 中身を出す。`/login` へ**送らない** |
| 3 | `GuestRoute` | true | `/timeline` へ送る。ログイン画面は**出さない** |
| 4 | `GuestRoute` | false | ログイン画面を出す。`/timeline` へ**送らない** |

> **react-router はモックにしない。** `MemoryRouter` に本物のルート定義を組めば
> 「ログイン画面が実際に出た」という**結果そのもの**を確認できる。
> モックにすると「`Navigate` という部品が呼ばれた」ことしか分からず、行き先が正しいかを確認できない。
> 代わりに `useAuth` だけをモックにする。本物を使うと `AuthProvider` と `localStorage` まで
> 巻き込み、落ちたときにどこが原因か切り分けられなくなる。

> **「送る」と「中身を出さない」を対で書く。** 前者だけだと、ログイン画面と中身が
> 両方出ている状態を見逃す。

### 12-8. jsdom に無いブラウザ機能の扱い

`PostSearchResults` は無限スクロールのため `IntersectionObserver`
（要素が画面に入ったことを知る仕組み）を使うが、テストを動かす jsdom にはこれが無く、
そのままでは描画した瞬間に落ちる。何もしない偽物を置いて描画できるようにする。

> **偽物は使う1ファイルの中に置き、`setup.ts` には入れない。**
> 共通設定に入れると、関係のないテストにまで偽物を持ち込むことになる。

## 13. フロントエンドの残りの部品とフック

12章までで扱わなかった部品とフック。**状態を持つもの**（`AuthProvider`）と
**副作用を扱うもの**（`useLogout` / `useInfiniteScroll`）が中心で、
「見た目」ではなく「**手順と後始末**」が主題になる。

### 13-1. ログイン情報の保存と復元（`AuthProvider`・デシジョンテーブル）

保存先は `localStorage`（ブラウザに残るメモ帳）のキー `raisetimeline.auth`。
**ブラウザを閉じても次に開いたときログインしたまま**にするための仕組み。

| # | 起動時の保存値 | 操作 | 期待 |
|---|---|---|---|
| 1 | 空 | ― | 未ログインで起動 |
| 2 | 正しい値 | ― | **ログイン状態を復元する** |
| 3 | **壊れた文字列** | ― | **未ログインで起動する**（例外で画面が真っ白にならない） |
| 4 | 空 | `login()` | ログイン状態になり、保存される |
| 5 | 正しい値 | `logout()` | 未ログインになり、**保存値も消える** |
| 6 | 正しい値 | `setAccessToken()` | アクセストークンだけ入れ替わり、**他は残る** |
| 7 | 空 | `setAccessToken()` | **何も起きない**（未ログインのまま） |
| 8 | 正しい値 | `updateUser()` | ユーザー情報だけ入れ替わり、**トークンは残る** |
| 9 | 空 | `updateUser()` | **何も起きない** |

> **#3 が要。** 保存値が壊れる原因は複数ある（別バージョンの形式が残っている、
> 手で書き換えられた、書き込み途中で閉じられた）。ここで例外が出ると**画面全体が真っ白**になり、
> 利用者は何もできなくなる。`try`/`catch` の `catch` 側を消すと、このテストだけが落ちる。

> **#6 と #8 で「他が残る」ことまで見る。** アクセストークンの入れ替えでリフレッシュトークンが
> 消えると、次の入れ替えができず結局ログアウトになる。**入れ替えは「作り直し」ではない。**

> **`localStorage` は偽物にしない。** jsdom に本物があり、保存先を直接見て確かめるほうが確実なため。

### 13-2. 失敗しても必ずログアウトする（`useLogout`・デシジョンテーブル）

| # | `refreshToken` | 通信 | 期待 |
|---|:---:|:---:|---|
| 1 | あり | 成功 | ログアウトAPIを呼ぶ → 認証状態を破棄 → `/login` へ |
| 2 | あり | **失敗** | **それでも**認証状態を破棄し `/login` へ |
| 3 | なし | ― | ログアウトAPIを**呼ばない**（失効させる対象が無い） |

> **#2 が仕様の中核。** サーバー側の失効に失敗したからといって画面に留まらせると、
> 「ログアウトを押したのにログインしたまま」になる。**手元の情報を捨てるのは通信の成否に関係なくできる。**
> `finally` を `catch` の後ろの通常処理に変えると、この2件（破棄・遷移）だけが落ちる。

> **画面遷移はモックで確かめる。** ここで見たいのは「どこへ送ったか」であり、
> 遷移先の画面が出ることではない（12-7 の門番とは逆の判断）。
> **`replace: true` まで見る。** 置き換えないと、戻るボタンでログアウト前の画面に戻れてしまう。

> **`isLoggingOut` は `true` のまま `false` に戻らない**（現状の挙動として記録）。
> ログアウト後は必ず画面が切り替わるため実害は無いが、
> 「戻る」と思い込んだテストを書くと嘘になる。

### 13-3. 監視の開始と後始末（`useInfiniteScroll`）

| 条件 | 期待 |
|---|---|
| `hasNext` が true | 監視を始める。監視対象はリスト末尾の印（センチネル） |
| `hasNext` が false | **監視を始めない**（読み終えた後も監視すると無駄な通信が続く） |
| 印が画面に入った | `onLoadMore` を呼ぶ |
| 印が画面に入っていない | **呼ばない** |
| 部品が取り外された | **監視をやめる**（`disconnect`） |
| 先読みの余白 | `rootMargin: '200px'`（画面に入る手前で読み始め、スクロールが止まって見えないように） |

> **観測役（`IntersectionObserver`）は自分で作り、「画面に入った」という知らせを手で起こす。**
> jsdom にこの仕組みが無いためだが、結果的に**実際にスクロールしなくても判断だけを確かめられる**。

> **フックが返す ref は、実際の要素に付いていないと監視が始まらない。**
> `renderHook` では要素に付けられないため、小さな部品を用意して本物のDOMに付ける。

### 13-4. Provider の外で使ったときのエラー（`useAuth`）

中身はほぼ `useContext` だが、判断が1つある。**`AuthProvider` の外側で使われたら例外を投げる**こと。

これが無いと `null` が返り、`user.displayName` のような読み取りで
「読めません」という分かりにくいエラーになる。**原因（囲い忘れ）から遠い場所で落ちる**ため直しにくい。
早い段階で、原因が書かれたエラーにして止めるほうがよい。

### 13-5. 削除ボタンの出し分け（`CommentList`）

| # | 条件 | 期待 |
|---|---|---|
| 1 | コメントの投稿者 == 閲覧者 | 削除ボタンを出す |
| 2 | コメントの投稿者 != 閲覧者 | **出さない** |
| 3 | `currentUserId` が `undefined` | **どのコメントにも出さない** |
| 4 | 0件 | 「まだコメントがありません。」（空のリストは「壊れている」ように見える） |

> 削除ボタンの見た目はゴミ箱の絵だけなので `aria-label` で何のボタンかを伝えている。
> 無いと読み上げでは「ボタン」としか分からない。

### 13-6. 編集ダイアログ（`PostEditModal`・境界値）

上限は新規投稿（`PostComposer`）と同じ 280文字。違いは2つある。

- **初期値が空ではなく「いま書いてある本文」**（少し直したい人が全部打ち直さずに済む）
- **失敗しても閉じない**（閉じると書き直した内容ごと消える）

| 入力 | 期待 | 狙い |
|---|---|---|
| 空 / 空白のみ | 保存できない | 下限の外・`trim()` の分岐 |
| 1文字 | 保存できる | 下限ちょうど |
| 280文字 | 保存できる・残り「0」 | **上限ちょうど** |
| 281文字 | **保存できない**・残り「-1」 | **上限の外** |

保存中は保存・キャンセルの**両方**を押せなくする（途中で閉じられると保存の成否が分からなくなる）。
連打しても `onSave` は1回。失敗しても本文は消えず、**もう一度保存できる**。

### 13-7. ダイアログの土台（`ModalOverlay`）

`role="dialog"` と `aria-modal="true"` を確かめる。
`aria-modal` が無いと、読み上げソフトは背後の内容も読み続けてしまう。
幅は既定値（`max-w-md`）と指定時の**両方**を確認する（既定値だけだと常に既定値を使う実装でも緑になる）。

### 13-8. テストの書き方で踏んだ2つの罠（記録）

**① デフォルト引数は `undefined` を渡しても適用される。**

```tsx
function renderList(comments: Comment[], currentUserId: number | undefined = MY_ID) { ... }
renderList([...], undefined)   // → currentUserId は MY_ID になる
```

「閲覧者が分からない状態」を作ったつもりが作れておらず、**偽の緑になりかけた**。
境界値のテストでヘルパーを使うときは、**省略記法を使わず必ず明示して渡す**。

**② `userEvent.type` は1文字ずつ打つ動きを忠実に再現する。**

280文字を入れると制限時間（5秒）を超えることがあり、しかも**同時に走る他のテストの負荷で
結果が変わる**。個別実行では通るのに全体実行では落ちる、たまに落ちるテスト（フレーキーテスト）になった。

**長い入力で確かめたいのは「その長さのときどう見えるか」であって打鍵の再現ではない。**
そこだけ `fireEvent.change` で値の変更を一度に起こす（11-2 で `accept` 属性の検証に
`fireEvent` を使ったのと同じ「目的に合う道具を選ぶ」判断）。

## 14. すべての層に共通するルール

1. **書いたテストは一度わざと失敗させ、赤を見てから緑にする。**
   一度も赤くなっていないテストは「実は何も検証していない」可能性を排除できない。
   **アサーションを壊すのではなく、本番コードを壊して落とす**ほうがよい。
   前者は「アサーションが動いている」ことしか証明しないが、後者は「このテストが何を守っているか」を証明できる。
2. **1テスト1検証。** Arrange（準備）→ Act（実行）→ Assert（検証）の3段で書く。
3. **実行順に依存させない。** 「他のテストが先に走ってデータを作ってくれる」ことを当てにしない。
   順序に依存した瞬間、たまに落ちるテスト（フレーキーテスト）になる。
4. **完了条件は「テストが通ること」ではなく「実行件数が表示されること」。**
