# テストケース設計

## RaiseTimeLine（仮称）

**この文書の役割:** 「どのテストケースを、なぜ選んだか」を残す。
テストの型・方針（どの層で何を確かめるか、使うアノテーション、命名規則）は
**`docs/tech-stack.md` の「バックエンドのテスト方針」「フロントエンドのテスト方針」が正本**なので、ここには書かない。

---

## 1. ケースの決め方

テストケースを思いつきで選ぶと、必ず抜けが出る。次の3つの技法で機械的に決める。

### 1-1. 同値分割

入力を「同じ結果になるグループ」に分け、**各グループから1つだけ**選ぶ。
投稿本文が「1〜280文字」なら、グループは3つ（短すぎ / ちょうどよい / 長すぎ）。
70文字と71文字を両方試すのは、同じグループなので無駄。

### 1-2. 境界値分析

**バグはグループの真ん中ではなく、切り替わり目に出る。**
`<=` と `<` の書き間違い、`length()` の数え方の間違いはすべて境目で起きる。
そこで各グループの**境目とその前後**を選ぶ。中間の値をいくつ試しても、この種の不具合は見つからない。

### 1-3. デシジョンテーブル

条件が複数あるときは、組み合わせを**表にして網羅**する。
「ログイン済み」「自分のものか」「存在するか」を頭の中で数えると必ず漏れる。
特に **403（権限がない）と 404（存在しない）の出し分け**は、表にしないと気づけない。

### 1-4. 「呼ばれないこと」の確認

例外が飛ぶことだけを確かめると、**「例外の前に書き込んでいた」場合を見逃す**。
弾いたときに、その先の処理（DB書き込み・ファイル保存・外部通信）が
呼ばれていないことを `verify(..., never())` で確かめる。

## 2. 投稿（`PostService` / `PostMapper`）

実装が持つ定数（`PostService.java`）: 本文の上限 **280文字** / ページの既定 **20件**・上限 **100件** / 新着取得の上限 **50件**

### 2-1. 本文の長さ（同値分割＋境界値）

| 入力 | 期待 | 狙い |
|---|---|---|
| `null` | `InvalidPostContentException` | 無効グループ |
| `""`・空白のみ・改行のみ | `InvalidPostContentException` | `isBlank()` の分岐 |
| 1文字 | 成功 | **下限ちょうど** |
| 280文字 | 成功 | **上限ちょうど** |
| 281文字 | `InvalidPostContentException` | **上限の外** |

### 2-2. ページサイズの正規化（境界値）

| `size` | 期待する要求件数 | 狙い |
|---:|---:|---|
| -1 | 21（既定20 + 1） | 負の値 |
| 0 | 21（既定20 + 1） | 下限の外 |
| 1 | 2 | **下限ちょうど** |
| 100 | 101 | **上限ちょうど** |
| 101 | 21（既定20 + 1） | **上限の外** |

> 常に「表示したい件数 + 1件」を要求する。余分に取れたかどうかで「次のページがあるか」を判定し、
> `COUNT(*)` を別途発行しないため。

### 2-3. ページ番号の正規化（境界値）

| `page` | 期待する `offset`（size=10） |
|---:|---:|
| -1 | 0（負は0ページ目として扱う） |
| 0 | 0 |
| 1 | 10 |
| 3 | 30 |

### 2-4. `hasNext` の判定（境界値）

**ここは20件と21件の境目でしか壊れない。**

| Mapper が返した件数（size=20） | `hasNext` | 画面に返す件数 |
|---:|---|---:|
| 0 | `false` | 0 |
| 20 | `false` | 20 |
| 21 | `true` | **20**（21件目は判定用なので返さない） |

新着投稿（上限50件）も同じ規則。**50件 → `hasMore=false` / 51件 → `hasMore=true`・50件を返す**。

### 2-5. 更新・削除の権限（デシジョンテーブル）

| # | 投稿が存在 | 自分の投稿 | 期待 | 確認すること |
|---|:---:|:---:|---|---|
| 1 | ❌ | − | `PostNotFoundException`（→404） | `updateContent` / `deleteById` を**呼ばない** |
| 2 | ✅ | ❌ | `PostAccessDeniedException`（→403） | 同上。画像削除も**呼ばない** |
| 3 | ✅ | ✅ | 成功 | 更新・削除が実行される |

> 投稿は公開情報なので、他人の投稿には 404 ではなく 403 を返して「権限がない」と明示する。
> 存在自体を隠したい種類のデータなら 404 に寄せる設計もある。

### 2-6. 画像の有無（デシジョンテーブル）

| 状況 | ファイル保存 | ファイル削除 |
|---|---|---|
| 画像なしで投稿 | **呼ばない** | − |
| 中身が空のファイルで投稿 | **呼ばない** | − |
| 画像ありで投稿 | 呼ばれる | − |
| **本文が不正で画像あり** | **呼ばない**（使われないファイルが残らないように） | − |
| 画像なしの投稿を削除 | − | **呼ばない** |
| 画像ありの投稿を削除 | − | 呼ばれる |

### 2-7. 新着件数の基準ID（境界値）

SQL は `id > afterId`。**基準となった投稿自身は数えない。**

| `afterId` | 期待 |
|---|---|
| 負の値 | 0 として扱う（初回読み込みと同じ） |
| 0 | 全件 |
| 最新の投稿ID | **0件**（新着なし） |
| 最新の1つ前のID | 1件 |

### 2-8. SQL の確認（`PostMapperTest`・実DB）

| 対象 | 確認すること |
|---|---|
| `insert` | `useGeneratedKeys` でIDがオブジェクトに書き戻される（直後に「作成した投稿を返す」ために必要） |
| `selectTimeline` | 新しい順・`LIMIT` で絞る・`OFFSET` で読み飛ばす・最終ページより後ろは空 |
| `selectTimeline` | いいね数／コメント数の集計・`likedByMe` が閲覧者ごとに変わる・未ログイン（`null`）でも動く |
| `selectFollowingTimeline` | フォロー中＋**自分の投稿**を含み、無関係な人は含まない |
| `selectByKeyword` | 中間一致・**`ILIKE` が大文字小文字を無視する**・エスケープ済み `%` が文字として扱われる |
| `updateContent` | 本文だけが変わり、画像はそのまま残る |

## 3. コメント（`CommentService` / `CommentMapper`）

本文の上限は投稿と同じ **280文字**。境界値も同じ（`null` / 空 / 1 / 280 / 281）。

### 3-1. 検証の順序

| # | 投稿が存在 | 本文 | 期待 | 理由 |
|---|:---:|---|---|---|
| 1 | ❌ | 不正 | **`PostNotFoundException`（404）** | 存在しない投稿に「本文が長すぎます」と答えるのは案内として誤り |
| 2 | ✅ | 不正 | `InvalidCommentContentException`（400） | |
| 3 | ✅ | 正常 | 成功 | |

### 3-2. 削除の権限（デシジョンテーブル）

| # | コメントが存在 | 自分のもの | 期待 |
|---|:---:|:---:|---|
| 1 | ❌ | − | `CommentNotFoundException`（→404）・**削除しない** |
| 2 | ✅ | ❌ | `CommentAccessDeniedException`（→403）・**削除しない** |
| 3 | ✅ | ✅ | 削除される |

### 3-3. SQL の確認

並び順は**古い順**（会話が上から読める順）。作成日時を明示して確認する
（`CURRENT_TIMESTAMP` はトランザクション開始時刻を返すため、続けて INSERT すると全部同じ時刻になる）。
投稿を削除するとコメントも `ON DELETE CASCADE` で消えることも確認する。

## 4. いいね（`LikeService` / `LikeMapper`）

### 4-1. 冪等性（このアプリの中核）

| 操作 | 期待 |
|---|---|
| 同じ人が2回いいね | **例外にならず件数は1のまま**（`ON CONFLICT DO NOTHING`） |
| 別の人がいいね | 件数が2になる（無視されるのは同一ユーザーの重複だけ） |
| いいねしていないのに取り消し | 例外にならない（0件削除） |
| 取り消し | 他人のいいねは消さない |

### 4-2. 存在確認の順序

投稿の存在確認を**先に**行う。後にすると、外部キー違反による 500 が 404 より先に発生してしまう。
→ 存在しない投稿へのいいねで `insertIgnoreDuplicate` が**呼ばれない**ことを確認する。

### 4-3. 件数と自分の状態は別の情報

`likeCount`（みんなの合計）と `likedByMe`（自分の状態）を取り違えない。
同じ投稿でも、見ている人によって `likedByMe` は変わる。

## 5. フォロー（`FollowService` / `FollowMapper`）

### 5-1. 自己フォローの防ぎ方（層の役割分担）

| 層 | 役割 | 確認すること |
|---|---|---|
| **Service** | **一次防衛** | `SelfFollowException` を投げ、**DBに問い合わせない** |
| DB（`ck_follows_not_self`） | 最後の砦 | Mapper を直接呼ぶと `DataIntegrityViolationException` |

> **DB制約に任せてはいけない理由:** `ON CONFLICT DO NOTHING` が無害化できるのは
> 一意制約違反（23505）だけ。CHECK制約違反（23514）は素通りして汎用ハンドラに落ち、**500** になる。

### 5-2. 向きの区別（非対称なデータで確認する）

フォローは「誰が誰を」の向きを取り違えやすく、**件数だけ見ていると気づけない**。
そこで**片思いの関係**を作って確認する。

| 一覧 | 含むもの | 含まないもの |
|---|---|---|
| `selectFollowing` | 自分がフォローしている人 | 自分をフォローしている人 |
| `selectFollowers` | 自分をフォローしている人 | 自分がフォローしている人 |

`followedByMe` は**閲覧者から見た関係**。相互フォローなら `true`、片思いされているだけなら `false`。

### 5-3. follow と unfollow の非対称性

`unfollow` には自己チェックが**無い**。解除は存在しない行を消すだけで害が無く、CHECK制約にも触れないため。
この違いは意図的なので、テストで固定しておく。

## 6. ユーザー・プロフィール（`UserService` / `UserMapper`）

### 6-1. @ユーザー名の重複判定（境界）

| 状況 | 期待 | 理由 |
|---|---|---|
| **自分が今使っている名前で保存** | **成功** | 除外しないと、表示名だけ直して保存しただけで409になる |
| 他人が使っている名前 | `UsernameAlreadyExistsException`（→409）・**更新しない** | |

### 6-2. アイコン更新の順序（順序そのものが仕様）

**「新ファイル保存 → DB更新 → 旧ファイル削除」**の順を守る。

> 逆順（旧削除が先）にすると、DB更新に失敗したときに**アイコンだけが失われる**。
> この不具合は「何が呼ばれたか」を見るだけでは検出できないため、`InOrder` で**順序**を検証する。

| 状況 | 旧ファイル削除 |
|---|---|
| 元々アイコンがある | 呼ばれる |
| 元々アイコンが無い | **呼ばない** |

### 6-3. 検索（`ILIKE`）

| 入力 | 期待 |
|---|---|
| `@ユーザー名`の一部 | 中間一致で見つかる |
| 表示名の一部 | 見つかる（username と display_name の OR 検索） |
| 大文字小文字を変えた語 | **見つかる**（`ILIKE` を使っているため） |
| エスケープ済みの `%`（`\%`） | **普通の文字として扱う**（`ESCAPE '\'` が効いていないと全件一致する） |
| 一致なし | 空のリスト（`null` ではない） |

## 7. 認証（`AuthService`）

### 7-1. 「何を返さないか」が重要

| 状況 | 期待 |
|---|---|
| メールアドレスが未登録 | `InvalidCredentialsException` |
| パスワードが違う | `InvalidCredentialsException`・**トークンを発行しない** |
| **上の2つのメッセージ** | **完全に同じ文言** |

> 「そのメールアドレスは存在しません」と返すと、**どのメールアドレスが登録済みかを教えてしまう**。

### 7-2. パスワードの保存

ハッシュが入っていることだけでなく、**生のパスワードが入っていない**ことも確かめる。
DBが漏れたときの被害の大きさが決定的に変わる部分のため。

### 7-3. リフレッシュトークン（デシジョンテーブル）

| # | トークンが存在 | 期限内 | ユーザーが存在 | 期待 |
|---|:---:|:---:|:---:|---|
| 1 | ❌ | − | − | `InvalidRefreshTokenException` |
| 2 | ✅ | ❌ | − | 例外 ＋ **そのトークンをDBから削除する**（使えない行を溜めない） |
| 3 | ✅ | ✅ | ❌ | `InvalidRefreshTokenException` |
| 4 | ✅ | ✅ | ✅ | 新しいアクセストークンを発行・**リフレッシュトークンは消さない** |

> **有効期限の判定は Service の責務で、SQL には期限の条件が無い。**
> `RefreshTokenMapperTest` で「期限切れでもレコードは返る」ことを明示的に確認し、
> 責任分担が変わっていないことを固定している。

## 8. 画像（`ImageValidator` / `LocalStorageService`）

### 8-1. サイズの上限（境界値）

上限は **5MB**（5,242,880バイト）。

| サイズ | 期待 |
|---|---|
| 0バイト | サイズを理由には拒否しない |
| ちょうど5MB | **受け入れる**（上限ちょうど） |
| 5MB + 1バイト | **拒否**（上限の外） |

### 8-2. 形式と拡張子（同値分割）

| Content-Type | 拡張子 | 期待 | 狙い |
|---|---|---|---|
| `image/jpeg` | `.jpg` / `.jpeg` | 受け入れ | |
| `image/png` | `.png` | 受け入れ | |
| `IMAGE/JPEG` | `.JPG` | 受け入れ | 大文字小文字を区別しない |
| `null` | `.jpg` | 拒否 | 未指定 |
| `text/plain` | `.txt` | 拒否 | 画像でない |
| `image/gif` | `.gif` | 拒否 | 画像だが許可外 |
| **`image/jpeg`** | **`.txt`** | **拒否** | **形式と拡張子の両方を見ている**（Content-Type は送信側が自由に名乗れる） |
| `image/jpeg` | なし | 拒否 | 拡張子が無い |

### 8-3. 保存（モックにしない）

「ファイルを保存する」処理をモックにすると、保存できたことにする処理をテストするだけになる。
`@TempDir` で一時ディレクトリに**実際に書き込んで**確認する。

| 確認すること | 理由 |
|---|---|
| 保存名が「UUID + 拡張子」 | |
| 元のファイル名を使わない | 同名衝突と日本語ファイル名を避けるため |
| 同名を2回保存しても両方残る | |
| 保存した中身が元と一致する | |
| **不正な形式ではファイルが作られない** | 例外だけ見ているとゴミファイルの残留を見逃す |
| 存在しないファイルの削除で例外を投げない | 削除は後片付け。失敗しても本来の処理は完了している |

## 9. 検索キーワード（`SearchKeyword`）

ここで防いでいるのは SQLインジェクションではない（MyBatis の `#{}` を使う限り起きない）。
防いでいるのは**「SQLは壊れないが検索の意味が壊れる」**問題。

| 入力 | 期待 | 狙い |
|---|---|---|
| `null` / `""` / 半角スペースのみ | `""`（空） | 呼び出し側が「DBに問い合わせない」と判断できる |
| `  鈴木  ` | `鈴木` | 前後の空白を除去 |
| `%` | `\%` | エスケープしないと `LIKE '%%%'` で全件に一致する |
| `_` | `\_` | LIKE では任意の1文字を表す記号 |
| `\` | `\\` | エスケープ文字そのものを打ち消す |
| **`\%`** | **`\\\%`** | **置換の順序の検証。** `\` を先に処理しないと、自分で足したエスケープ文字まで二重に変換されて意味が壊れる |

### 既知の課題

**全角スペース（U+3000）だけの入力は空扱いにならない。**
実装が使う `String#trim()` は U+0020 以下の文字しか取り除かないため。
半角スペースは空扱いなのに全角は違う、という不揃いな状態になっている。
直すなら `trim()` を `strip()`（Unicode対応版）に替えるだけだが、本番の振る舞いが変わるため、
テスト追加とは別に対応する。現状は `SearchKeywordTest` に「現状の挙動」として記録してある。

## 10. すべての層に共通するルール

1. **書いたテストは一度わざと失敗させ、赤を見てから緑にする。**
   一度も赤くなっていないテストは「実は何も検証していない」可能性を排除できない。
   **アサーションを壊すのではなく、本番コードを壊して落とす**ほうがよい。
   前者は「アサーションが動いている」ことしか証明しないが、後者は「このテストが何を守っているか」を証明できる。
2. **1テスト1検証。** Arrange（準備）→ Act（実行）→ Assert（検証）の3段で書く。
3. **実行順に依存させない。** 「他のテストが先に走ってデータを作ってくれる」ことを当てにしない。
   順序に依存した瞬間、たまに落ちるテスト（フレーキーテスト）になる。
4. **完了条件は「テストが通ること」ではなく「実行件数が表示されること」。**
