# 運用設計書

## 1. 本書の目的・スコープ

RaiseTimeLineを実際に動かし続けるうえでの「ログをどう設計しているか」「何を監視すべきか」
「障害が起きたときどう対応するか」をまとめたドキュメント。

**対象:** バックエンド（Spring Boot）のみ。フロントエンドは対象外。

**今回やること:**
- ログレベルの使い分け・構造化ログ・相関ID・機密情報マスキングの設計と実装
- 監視項目・閾値・障害対応フローの**ドキュメントレベルの設計**

**今回やらないこと:**
- Datadog等の監視SaaSの実導入（アカウント作成・実際の連携設定）
- メトリクス収集・分散トレーシングの実装
- アラート通知の実装（Slack通知・メール通知等）

外部サービスの実導入を含まないため、本Issueの作業に有料APIの利用確認は不要。

## 2. ログ設計

### 2.1 ログレベルの使い分け方針

「誰が・いつ対応する必要があるか」で決める。HTTPステータスとの対応関係は
[design.md「5. エラーレスポンス形式」](./design.md#5-エラーレスポンス形式)の一覧を参照（重複させない）。

```
このログを見て人間が「今すぐ」動く必要があるか？
├─ Yes → ERROR（想定外の例外。スタックトレース付き）
└─ No
   ├─ 頻発したら運用側が気付きたい変化か？（起きても正常だが監視したい）
   │  → WARN（想定内の業務ルール違反・認証失敗。スタックトレースなし1行）
   ├─ 一度きり／取り消せない／監査価値が高い操作か？
   │  → INFO（登録・投稿作成・削除・ログイン成功など）
   └─ 開発時にだけ追いたい詳細か？
      → DEBUG（SQL発行内容など。本番では出さない）
```

**据え置き（意図的にログを出さないもの）:**

| 対象 | 理由 |
|---|---|
| 400系の純粋な入力バリデーション（`MethodArgumentNotValidException` `InvalidPostContentException` `InvalidImageException` `InvalidCommentContentException` `SelfFollowException` `MaxUploadSizeExceededException`） | クライアントの入力ミスであり、運用側が見ても対応できるアクションが無い。ログに残すとノイズになり、本当に対応が必要なWARN/ERRORが埋もれる |
| いいね・フォロー・コメント作成 | 高頻度・低重要度の操作。すべて記録すると量が多く、本当に重要な投稿作成・削除のログが埋もれる。将来「いいね数の急増を監視したい」等の要件が出れば追加を検討する |
| 未ログイン状態でのアクセス（トークン無し） | 日常的に発生する正常な状態（トップページの閲覧など）であり、異常ではない |
| `update()`（投稿編集） | 取り消し可能な操作であり、作成・削除と比べて監査価値が低いと判断した |

### 2.2 構造化ログの形式

Spring Boot 3.4がネイティブでサポートする構造化ログ機能を使用する（追加ライブラリ不要）。

| プロファイル | 設定ファイル | ログレベル | 出力形式 |
|---|---|---|---|
| 未指定（ローカル開発） | `application.yml` | root: INFO / 自パッケージ: DEBUG | 人間可読なコンソール出力 |
| `prod` | `application-prod.yml` | root: INFO / 自パッケージ: INFO | JSON形式（Logstash構造化ログ） |

**プロファイル未指定を既定にしている理由:** 「うっかり本番相当のログ量になる」ではなく
「うっかり開発相当のまま」という安全側に倒した設計判断。JSON化を本番プロファイルに
閉じ込めることで、ローカル・CIのコンソールがJSON文字列だらけになってスタックトレースが
読みにくくなる事態を避けている。

**構造化ログ（JSON形式）を採用する理由:** 文字列ログは機械集計のために正規表現パースが
必要で、文言を変えると集計が壊れる。JSON形式ならフィールドが最初から独立しているため、
`level:ERROR AND userId:123` のような検索がそのまま可能になる。「Datadogを導入する」のではなく
「導入したときにすぐ使える出力形式にしておく」という配線だけを今回済ませている
（実際の切替配線はデプロイフェーズの作業）。

**`SPRING_PROFILES_ACTIVE=prod`で本番プロファイルを有効化する。** 実際にEC2側でこの環境変数を
設定する作業はデプロイフェーズ（フェーズ07）で行う。

### 2.3 相関ID（requestId）とMDCの設計

複数ユーザーが同時にアクセスすると、ログはリクエストをまたいで時系列に混ざって出力される。
`RequestIdFilter`（`backend/src/main/java/com/raisetech/raisetimeline/logging/`）が
リクエストごとに`UUID`を発行し、`MDC`（スレッドローカルな変数）に積むことで、
以降のすべてのログ行に自動で`requestId`が乗るようにしている。

| 項目 | 内容 |
|---|---|
| 生成元 | 常にサーバー側で`UUID.randomUUID()`により生成する。クライアントが送ってきたヘッダーは信用しない（ログ偽装対策） |
| クライアントへの返却 | レスポンスヘッダー`X-Request-Id`に設定する。問い合わせ時にこのIDを伝えてもらえば該当ログをすぐ検索できる |
| クリア | `finally`ブロックで必ず`MDC.remove()`する。Tomcatはスレッドを使い回すため、クリア漏れは「別リクエストのログに前のIDが紛れ込む」という発見しづらいバグになる |
| 認証済みユーザーの追跡 | `JwtAuthenticationFilter`が有効なトークンを検証できたときだけ`userId`もMDCに積む。ログイン自体のリクエストや未ログインアクセスでは`userId`は空になる |
| 人間可読コンソールへの表示 | `application.yml`の`logging.pattern.level`に`[reqId:%X{requestId}] [userId:%X{userId}]`を明示的に組み込んでいる。MDCに積むだけでは人間可読形式には表示されないため（本番のJSON形式はMDCの値が自動でフィールドに乗るため不要） |

**将来フロントエンド連携時の拡張ポイント:** 現在はサーバー側生成のみだが、フロントエンドが
先にIDを発行してヘッダーで送る構成に変える場合は、サーバー側での検証（形式チェック等）を
追加する必要がある。今回はスコープ外。

### 2.4 ログに含めないもの（機密情報マスキング方針）

| 分類 | 具体例 | 対応 |
|---|---|---|
| 認証情報 | パスワード（平文・ハッシュ問わず）、JWTトークン本体、署名鍵 | 一切ログに出さない。`JwtAuthenticationFilter`のWARNログもトークンの値ではなくパス（`path=`）のみを出す |
| 個人情報 | メールアドレス | ユーザー登録・ログインのINFOログは`userId`のみを出し、メールアドレスは出さない |
| 投稿本文・コメント本文 | ユーザーが入力した自由記述 | ログに含めない（`postId`などのIDのみ） |

**回帰防止の仕組み:** `NoSensitiveDataInLogsTest`
（`backend/src/test/java/com/raisetech/raisetimeline/logging/`）が、`backend/src/main/java`配下の
ソースコードを静的に走査し、`log.info/warn/error/debug(...)`の呼び出し行に`password`/`token`/`secret`
という識別子（大小文字無視）が含まれていないかを機械的にチェックする。将来ログ出力を追加する
実装者が誤って機密情報を渡してしまっても、このテストがビルド時に検知する。

> **検出範囲の限界:** 1行で書かれたログ呼び出しのみを検出対象としている。将来ログ呼び出しが
> 複数行にわたる書き方に変わった場合はこの検出をすり抜けるため、その限界を認識しておく。

### 2.5 ログの保存・ローテーション

**現状:** 標準出力（コンソール）にのみ出力する。ファイルへの書き出し設定は無い。

**将来（EC2デプロイ時の前提）:** systemdサービスとして起動する場合、標準出力は`journald`が
自動的に保持する。ログローテーション（古いログの自動削除）の設定は、デプロイフェーズで
[infrastructure.md](./infrastructure.md)側の作業として検討する（本書ではリンクのみ）。

## 3. 監視の3本柱

監視は「ログ」「メトリクス」「トレース」の3つが揃って初めて機能する。

| 柱 | 何を見るか | 実装状況 |
|---|---|---|
| ログ | 個々の出来事の詳細（いつ・誰が・何をした・何が失敗したか） | **実装済み**（本書2章） |
| メトリクス | 数値の傾向（エラー率・レスポンスタイム・リソース使用率） | **未実装** |
| トレース | 1リクエストが複数サービスをどう通過したか | **未実装** |

**正直な現状評価:** 「気づく（メトリクス）→ 掘る（ログ）」というサイクルには本来この2つが
必要だが、現時点ではログしか実装されていない。ログだけでは異常の発生自体に気づきにくく
（大量に出力される中から手動で見つける必要がある）、「監視の1/3しか揃っていない」状態にある。

**トレースの優先度が低い理由:** 分散トレーシングは複数のサービス（マイクロサービス）をまたぐ
処理の追跡に真価を発揮する。RaiseTimeLineはEC2 1台構成のモノリスであり、1リクエストは
基本的に1プロセス内で完結するため、現時点での導入効果は限定的と判断した（Micrometer Tracing
導入を見送った理由も同じ）。

## 4. 監視項目・閾値の設計（ドキュメントレベル）

実装・アラート設定は含まない、一般的なWebアプリケーションを前提にした設計のみ。

### 4.1 可用性・エラー系

| 項目 | 閾値の考え方 |
|---|---|
| 5xx率 | 全リクエストに対する5xx応答の割合。個人開発規模では「5分間で5xx率が5%を超えたら注意」程度が目安 |
| ヘルスチェック | Spring Boot Actuatorの`/actuator/health`相当のエンドポイントが応答すること（ALBのヘルスチェックと連動） |

### 4.2 性能系

| 項目 | 閾値の考え方 |
|---|---|
| p95レスポンスタイム | 95%のリクエストがこの時間以内に応答している値。個人開発規模では「p95が1秒を超えたら注意」程度が目安 |
| p99レスポンスタイム | 外れ値も含めた応答時間。p95との差が大きい場合、一部の重いクエリやN+1問題を疑う |

### 4.3 リソース系

| 項目 | 閾値の考え方 |
|---|---|
| DB接続プール使用率 | プールの上限に近づくと新規リクエストが待たされる。使用率80%超で注意 |
| JVMメモリ（ヒープ使用率） | 継続的に高止まりする場合はメモリリークを疑う |
| ディスク使用量 | ログ・アップロード画像（ローカル保存時）で肥大化する可能性。80%超で注意 |

### 4.4 個人開発規模での閾値の考え方

**「常時人間が張り付いて監視する」前提ではない。** 個人開発・小規模運用では、閾値は
「異常に気づくための粗い網」であればよく、企業のSREのような厳密なSLO運用は過剰である。
まずログでエラーの有無を追える状態（本書2章）を土台とし、メトリクス・アラートは
実際に運用してから必要性を感じた項目を優先的に導入する方針が現実的。

## 5. 障害対応フロー

```
検知 → 一次切り分け → 対応 → 復旧確認 → 振り返り
```

1. **検知:** ユーザーからの報告、または（将来）アラート通知
2. **一次切り分け:** ログを`requestId`または`userId`で検索し、いつ・どのリクエストで
   何が起きたかを特定する。`ERROR`ログがあればスタックトレースから原因箇所を絞り込む
3. **対応:** 原因に応じて対処（アプリの不具合→修正してデプロイ／DBの問題→接続確認／
   一時的な負荷集中→リソース確認）
4. **復旧確認:** 同じ操作を再現して正常応答を確認し、以後のログにエラーが再発しないことを見る
5. **振り返り:** 原因・対応・再発防止策を記録する。ログに必要な情報が不足していた場合は
   ログ設計自体の見直し（本書2章の更新）につなげる

### 典型パターン別チェックリスト

| 症状 | 確認すること |
|---|---|
| 特定ユーザーだけ操作できない | そのユーザーの`userId`でログを検索。`403`（`PostAccessDeniedException`等）のWARNが出ていないか |
| ログイン後すぐログアウトされる | JWTの有効期限設定（`jwt.access-token-validity`）を確認。`JWTの検証に失敗しました`のWARN頻度を見る |
| 特定の操作だけ遅い | Mapper層のSQL（DEBUGログ）を確認。N+1問題やインデックス不足を疑う |
| 500エラーが多発 | `予期しないエラーが発生しました`のERRORログとスタックトレースを`requestId`で1件ずつ確認 |

## 6. 将来のDatadog連携方針

**今回導入しない理由:** 個人開発規模・EC2 1台構成では、Datadog等の有料監視SaaSの
費用対効果が低い。まずは無料で使える構造化ログ・標準出力ベースの運用で十分と判断した。

**将来つなぐ手順（概要）:** 本番プロファイルはすでにLogstash JSON形式で出力しているため、
Datadog Agentを導入してログの取り込み設定（`conf.d`にログソースを追加）をするだけで
連携できる。アプリケーションコードの変更は不要な設計にしてある。

**Micrometer Tracing見送り理由:** 3章で述べた通り、EC2 1台のモノリス構成では分散トレーシングの
効果が薄く、導入・学習コストに対して得られる価値が小さいと判断した。将来サービスを分割する
（マイクロサービス化する）場合には再検討する。
