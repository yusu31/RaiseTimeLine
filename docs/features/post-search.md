# 機能詳細設計: 投稿検索（F-09）

## 概要

投稿本文をキーワードで検索できる。ヘッダーの🔍から検索画面（`/search`）を開き、「投稿」タブで検索する。
「ユーザー」タブに切り替えるとユーザー検索（F-10）になる。

検索結果はタイムラインと同じ投稿カードで表示するため、いいね・コメント数の確認、
自分の投稿の編集/削除、投稿詳細やプロフィールへの遷移がその場で行える。

## 技術方針

### 検索は `ILIKE` の中間一致で行う

```sql
WHERE p.content ILIKE '%' || #{keyword} || '%' ESCAPE '\'
```

投稿本文は「長い文章の途中に検索語が現れる」ため、前方一致では使いものにならない。中間一致が必須。

`ILIKE` は PostgreSQL の「大文字小文字を区別しない `LIKE`」。`LOWER(content) LIKE LOWER(...)` と書く手もあるが、
**列に関数をかけると通常のインデックスが使えなくなる**。F-10 ユーザー検索と同じ判断。

### PostgreSQL 標準の全文検索（`tsvector` + GIN）は採用しない

標準の全文検索は「空白で区切られた単語」を前提としており、**空白のない日本語では実質機能しない**。
`今日は良い天気` が1つの塊として扱われ、「天気」で検索しても引けない。

日本語対応には `pg_bigm` / `PGroonga` などの拡張が必要だが、

- 公式 Docker イメージに含まれないため、イメージの自前ビルドが必要になる
- デプロイ先の RDS で同じ拡張が使えるかの確認が要る

現在の規模に対して代償が大きいため、`ILIKE` の中間一致で足りると判断した。

### 高速化（`pg_trgm`）は本機能に含めない

`LIKE '%...%'` は通常の B-tree インデックスを使えないため、投稿数が増えると遅くなる。
`pg_trgm` 拡張（PostgreSQL に標準同梱）と GIN インデックスで解決できるが、
**機能追加と性能改善を1つの変更に混ぜない**方針により別課題とした。実際に遅くなってから対応する。

### `<if>` を使わず独立した `<select>` を足す

タイムライン用の `selectTimeline` に検索条件を足すのではなく、`selectByKeyword` を新設した。
`selectByAuthorId` / `selectFollowingTimeline` と同じ扱いで、`docs/tech-stack.md` の
「1ステートメント1目的」方針に従う。JOIN と集計のブロックは重複するが、SQL単体で読めることを優先する。

### LIKEのエスケープを `SearchKeyword` に共通化した

`%` と `_` は `LIKE` のワイルドカード。エスケープしないと **`%` の1文字検索が `LIKE '%%%'` となり全投稿に一致する。**

この処理は F-10 実装時に `UserService` の private メソッドとして書かれていた。投稿検索でも同じものが要るため、
`service/SearchKeyword.java` に切り出して両者で共有している（`ImageValidator` と同じ考え方）。
コピーすると「片方だけ修正して挙動がずれる」事故が起きるため。

```java
return trimmed
        .replace("\\", "\\\\")   // ← 必ず最初に置換する
        .replace("%", "\\%")
        .replace("_", "\\_");
```

**バックスラッシュを最初に置換する。** 順番を逆にすると、後の処理が「自分で足したエスケープ文字」まで
二重に変換して意味が壊れる。

なお `#{keyword}` を使っている限り **SQLインジェクションは発生しない**。
これは「SQLは壊れないが検索の意味が壊れる」という別種の問題。

### 空のキーワードではDBに問い合わせない

`SearchKeyword.normalize()` は null・空文字・空白のみに対して空文字を返す。
呼び出し側は戻り値が空かどうかだけを見て「DBに問い合わせない」判断ができる。

Controller では **`q` が空文字でも「検索」として扱う**。ここで全件を返すと、
検索欄が空なのに全投稿が並ぶという意図しない画面になるため。

### `q` と `timeline` が同時に来たら `q` を優先する

利用者がキーワードを入力したという明示的な意思表示のほうが強いため。
分岐は Controller で行う（クエリ文字列の解釈は Controller の責務）。

### 検索結果に専用のレスポンスクラスを作らない

タイムラインと同じ `PostListResponse`（`posts` / `page` / `hasNext`）をそのまま返す。
返す内容が同じなのでクラスを増やさない。F-10 で `User` をそのまま返したのと同じ判断。

### ページングはタイムラインと同じ `LIMIT/OFFSET` 方式

ユーザー検索は上限50件で打ち切っているが、投稿は件数が増えやすく、
打ち切ると「あったはずの投稿が見つからない」が起きる。無限スクロールで全件到達できるようにした。

`hasNext` の判定は既存と同じく **欲しい件数より1件多く取得する**方式（`size + 1`）。
`COUNT(*)` を別に発行しないため軽い。

### タブごとにコンポーネントを分けて状態の混入を防ぐ

```
SearchPage.tsx            ← 検索ボックス・タブ・キーワードを持つ（親）
├─ PostSearchResults.tsx  ← 投稿の結果とページ位置を持つ
└─ UserSearchResults.tsx  ← ユーザーの結果を持つ
```

親はタブに応じて**どちらか片方だけを描画する**。React は非表示側をアンマウントするため、
そのコンポーネントが持っていた結果・ページ位置は自動的に破棄される。

1つのコンポーネントで両タブを扱うと、投稿タブで3ページ目まで読んだ状態が残り、
戻ってきたときに4ページ目から読み込んで**投稿が歯抜けになる**。
これは PR #52 でタイムラインの「全体／フォロー中」タブに実際に起きた不具合と同じ構造のため、
注意ではなく**構造で**防いでいる。

### 入力は300msデバウンスする

F-10 と同じ。打鍵のたびにAPIを呼ばないよう、入力が止まってから検索する。
デバウンスは親（`SearchPage`）が担当し、子にはデバウンス済みのキーワードだけを渡す。

## API

`GET /api/posts?q={keyword}&page=&size=`（認証必須）。
レスポンス例とステータスコードは [docs/design.md](../design.md) の「レスポンス例」を参照。

## 画面

`SearchPage`（`frontend/src/pages/SearchPage.tsx`）と、タブごとの
`PostSearchResults` / `UserSearchResults`（`frontend/src/components/`）。
ワイヤーフレームは [docs/screen-design.md](../screen-design.md) の WF-06。

F-10 実装時の `UserSearchPage.tsx` は、中身を `UserSearchResults.tsx` へ移して削除した。

## 将来課題

| 項目 | 内容 |
|------|------|
| インデックスが効かない | `ILIKE '%...%'`（中間一致）は B-tree インデックスを使えない。投稿数が増えたら `pg_trgm` 拡張と GIN インデックスを検討する（SQLは変更せずに済む） |
| 検索キーワードがURLに残らない | `/search?q=...` にしていないため、検索結果を共有できずリロードで消える。F-10 と共通の課題 |
| タブの状態がURLに残らない | 同上。どちらのタブを見ていたかもリロードで初期化される |
| ページングが `LIMIT/OFFSET` 方式 | 深いページほど遅くなる。タイムラインと共通の課題（[timeline-sync.md](./timeline-sync.md)） |
